# Netlify + Paystack test payment architecture

This branch implements audit A01/A02 for review. It is **test-mode only**, with all real package billing configurations disabled pending commercial approval. No live settings, credentials, transactions, merges or deployments are part of this work. `netlify.toml` deliberately uses `ignore = "exit 0"` to skip automatic branch builds/deploy previews. An approved future release must explicitly remove that guard. Existing Netlify dashboard configuration remains untouched.

## Implemented flow

1. The existing package drawer, navigation, tier cards and styles remain. The one-time Swagger/Frontline selection hides duration controls; obsolete hardcoded discount labels are removed. Invoice values come only from `payment-quote`, never from displayed card prices. Unapproved catalog entries display an explanation and keep payment disabled. Unsupported/invalid durations are rejected by the server even if browser controls are edited.
2. `payment-initialize` validates a package/tier/duration/media-budget selection against the private versioned catalog, recomputes integer kobo totals, validates customer data, and writes an immutable invoice snapshot to PostgreSQL **before** calling Paystack. Any client `amount`, currency, metadata, reference or callback URL is ignored. The reference is server-created. No Paystack plan or recurring authorization is created.
3. A random 256-bit checkout request key binds retries to an identical selection/customer. Only its hash is stored. A database unique constraint arbitrates parallel initialization. The same request returns its existing provider URL; changed payloads are rejected. If provider initialization times out after order creation, repeat requests do not initialize another reference or assume success: they require reconciliation. The original attempt may already exist at Paystack. Do not start a replacement payment until the reference is checked.
4. Checkout hands off to the server-initialized Paystack hosted page instead of the old live Inline v1 popup. This is the deliberate UX change: it avoids loading a live publishable key and preserves the drawer/order form. Only an HTTPS `checkout.paystack.com` authorization URL returned by the server is accepted.
5. Initialization sets a Secure/HttpOnly/SameSite=Lax `__Host-wt-order` cookie. Paystack returns to `welcome.html?reference=...`. The reference alone is **not** authorization; status requires the order-bound browser cookie. No customer data or payment proof is put in URLs. Legacy `session_id` Base64 tokens are not recognized. The cookie has a one-day technical session lifetime, not a contract term. This flow supports the current checkout browser, not cross-device account recovery; a later checkout replaces that browser's cookie. Support recovery needs a separately approved authenticated flow.
6. `payment-status` and the signed webhook call Paystack's verify API. A successful transaction must match the stored reference, exact amount, currency, customer email, test domain, package, tier, catalog version and duration. Package metadata is generated by the server at initialization and compared against the durable snapshot, not the current catalog or browser claim. Non-success statuses never unlock onboarding. Transaction IDs are preserved as strings, including unsigned 64-bit values.
7. Settlement updates the order and inserts one outbox record in a single PostgreSQL transaction. Conditional update + primary/unique constraints protect against simultaneous callbacks, webhook retries and reuse of one Paystack transaction ID for another order. Paid is terminal here; replays do not issue another outbox event. The outbox is durable, but no email, provisioning or fulfillment worker is enabled. A future worker must use the reference as its downstream idempotency key; delivery is not automatically exactly-once.
8. Welcome loads the existing public Tally questionnaire only after authenticated server verification and strips query identifiers first. It sends no customer PII to the form URL. The questionnaire is public and is not itself an authenticated entitlement or proof that submissions are paid. Any future fulfillment/admin process must look up the paid order server-side; never trust a Tally submission as payment evidence.

Orders are not stored in Function memory, browser storage or an ephemeral filesystem. A warm PostgreSQL pool is only a connection cache. Database outages fail closed. No automatic refund, renewal or subscription policy is introduced.

## Current documented webhook verification

Reviewed Paystack's official [webhooks documentation](https://paystack.com/docs/payments/webhooks/) and [Transaction API](https://paystack.com/docs/api/transaction/) on 2026-11-06.

The current `Paystack-Signature` format contains `t=<unix seconds>,v1=<key id>:<hex signature>`. Verify HMAC-SHA512 over `t + '.' + exact raw body bytes`, keyed by the full `whsec_...` secret. Reject timestamps outside ±300 seconds and compare valid 128-character hex signatures using constant-time equality. Multiple signatures/secrets support rotation. JSON is parsed **after** checking the raw bytes, including Netlify's base64 body representation. Invalid modern signatures never fall back to legacy.

For test accounts that still send only `x-paystack-signature`, explicitly set `PAYSTACK_ALLOW_LEGACY_WEBHOOK=true`; the legacy method checks HMAC-SHA512 over raw bytes using the Paystack test secret key. Default is disabled. It has no signed timestamp; database settlement idempotency is therefore essential. Switch it off once the account sends the modern header.

The Function waits for durable verification/settlement before returning 200; it does not acknowledge and launch an unawaited task that Netlify may terminate. Invalid signatures return 401. Unsupported events and unknown references are acknowledged without state changes. Transient API/database failures return a non-200 response so Paystack can retry. A matched order with a verification mismatch is not marked paid and needs investigation; no raw payload/PII/credential logging is added. Bound API/DB timeouts keep processing short. There is no background queue worker in this change.

## Setup for a future authorized test environment

Nothing in this section was applied to a hosted account.

1. Use Node 22+, `npm ci --ignore-scripts`, and an isolated Netlify site/test context. Do not reuse production secrets or production order storage. Preserve the build-ignore guard until test deployment is explicitly authorized. A plain static HTTP server cannot execute Functions. Netlify CLI/dev needs separate installation and HTTPS handling for the Secure `__Host-` cookie; do not weaken cookies to make HTTP work.
2. Provision a durable PostgreSQL database (for example a dedicated managed PostgreSQL/Neon database) reachable by Netlify Functions. The checked-in adapter uses `pg`, verifies TLS certificates, and supports pool reuse. Use a trusted server certificate/CA, a pooled connection endpoint and a dedicated non-superuser role. Do not put `sslmode=no-verify` or conflicting SSL overrides in the URL. Define backup/restore, access control and retention with the owner.
3. Apply `migrations/001_orders.sql` once using an administrative migration role. Grant the Function role SELECT/INSERT and only the required UPDATE columns (`authorization_url`, `status`, `transaction_id`, `paid_at`) on `payment_orders`; SELECT/INSERT on `payment_outbox`. Do not grant schema alteration, arbitrary invoice-column updates or deletion to the Function role. Migration is never run by a Function. Restrict database and dashboard access; the records contain customer PII. Commit migration changes before changing the runtime schema. Do not expose SQL or backend files in the public site.
4. Configure these environment variables in the **test Functions context**, never in browser JavaScript or committed `.env` files:

| Variable | Value / purpose |
| --- | --- |
| `PAYSTACK_SECRET_KEY` | Paystack **test** secret (`sk_test_...`). Any live key is rejected in code. |
| `PAYSTACK_WEBHOOK_SECRETS` | Full test webhook signing secret(s) `whsec_...`, comma-separated during rotation. |
| `PAYSTACK_ALLOW_LEGACY_WEBHOOK` | `false` by default; explicitly `true` only during the documented legacy test-account migration. |
| `PAYMENT_SITE_ORIGIN` | Exact HTTPS test-site origin, no trailing slash/path. Browser Origin and callback target are fixed to it. |
| `DATABASE_URL` | Test-only PostgreSQL connection string; certificate verification remains enabled. |

5. After authorization to deploy a test environment, configure its **test-mode** Paystack webhook endpoint as `https://<test-host>/.netlify/functions/payment-webhook` for `charge.success`. Obtain the test signing secret from Developers → API configuration and confirm actual event headers. No dashboard change is performed by this branch. Callback URL is set server-side to the exact test origin's `/welcome.html`. Do not configure a production webhook for this test-only implementation.
6. Approve and enter the catalog rules described below, and then exercise provider test cards only after separate authorization for a test deployment. All validation for this PR uses mocked Paystack responses; it makes no Paystack API requests.
7. `scripts/build-public.cjs` copies only the site's existing static files to `public/`; Netlify publishes that directory and bundles Functions separately. This prevents serving server source, SQL, tests, dependencies or config from the repository root. Verify the effective publish directory in any future test build, especially if the dashboard overrides repo settings. Do not deploy the repository root.

## Commercial decisions still blocked

Every catalog package is `approved:false`. No existing advertised fee/minimum/discount has been silently adopted as authoritative. Browser selection does not bypass this. The checkout therefore cannot initialize any current package until the owner approves its rule set; missing test credentials/storage also fail closed.

For **each package and tier**, approve:

- Version identifier and fee in integer kobo; one-time versus time-based fee. Existing UI labels identify Swagger/Frontline as one-time; other product scope and Cashflow's billing basis still need confirmation.
- For time-based billing: contract minimum versus months payable now, permitted prepaid durations, whether monthly collection during a longer commitment is needed, and exact discount (including explicitly zero) for every permitted duration.
- Media budget minimum/maximum and whether it is collected by Webtellisense or paid directly to platforms; whether it scales by prepaid months and whether any discount applies. The current engine discounts only service fees and multiplies media by prepaid months; enable it only if that model is approved.
- Any renewal/subscription mandate, refunds, cancellation, ownership and tax/fee disclosures. None are invented or automated here. `prepaid_months` is a single upfront charge for approved months, **not** automatic recurring billing or a subscription. If the approved model requires automatic renewals, additional Paystack plan/subscription lifecycle work and authorization are required.

Configuration shape (use approved numbers, not test-fixture values): `version`, `packages[id].approved`, `billingMode` (`one_time` or `prepaid_months`), `minimumMonths` and `allowedMonths` for prepaid, explicit `discountBpsByMonths` (basis points; 0 means no discount), and `tiers[tier].feeKobo`, `adMinKobo`, `adMaxKobo`. One-time orders require duration 1 and are never multiplied or granted duration-based discounts implicitly. The engine rounds an explicitly approved percentage discount down to whole kobo. Agree to that rounding rule before enabling percentage discounts. Current browser duration choices are 1/3/6; adapt their labels/options only to the final approved configuration. Mismatched choices remain rejected.

## Tests and operational limits

`npm test`: mocked provider plus PostgreSQL-compatible in-process SQL tests, pricing/tampering, order binding, signature raw bytes/timestamps/rotation/legacy, handler authorization, replay/outbox and static-publish checks. Test catalog numbers are fictional fixtures and never loaded by deployed handlers. `npm run test:db` runs a real PostgreSQL concurrency/rollback suite only when `TEST_DATABASE_URL` targets a dedicated disposable local test database. It creates/drops a uniquely named schema. Never point it at production.

Before any deployment, still verify browser/hosted test checkout and cancellation/return, secure cookie behavior, accessibility/mobile layouts, actual Netlify bundling and test-database TLS, webhook delivery/retry timing, provider metadata and test receipts. Add platform rate limits/abuse controls appropriate to the Netlify plan before exposing initialization publicly; exact-origin checks are CSRF protection, not bot authentication. Monitoring, reconciliation of pending initializations, outbox delivery and authenticated cross-device recovery need an operational plan. Refund/dispute lifecycle and ongoing subscription access are outside this prepaid-payment implementation. No live mode is enabled.
